# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Barbos — a Telegram Mini App (in Russian) that reminds a *family* (not a group chat) to walk the dog, tracks who walked it and when (with duration/notes), and tracks medical treatments (ticks/deworming/vaccines). All UI (onboarding, logging walks, medicine, stats) lives in a Telegram Mini App backed by a REST API; the bot (`bot.py`) is only the entry point (`/start`) and the push-notification channel.

See `TZ_Barbos_MiniApp.md` (gitignored — private planning doc, not in the repo history) for the full spec this was built against.

## Architecture — two independent processes, one Postgres

```
bot.py            → /start (WebApp button) + reminder scheduling/sending
api/main.py        → FastAPI: REST API + serves miniapp/ as static files
database.py          → shared data-access layer, imported by BOTH bot.py and api/*
```

`bot.py` and `api/main.py` are meant to run as **separate deployments** (two Railway services in production — see README). Neither touches `psycopg2` directly; both go through `database.py`'s functions (`create_family`, `add_walk`, `get_stats`, etc.). This matters because the two processes don't share memory — see "Reminder scheduling" below for why that shapes the design.

- `database.py` — all Postgres access via `psycopg2`, connection string from `DATABASE_URL`, borrowed from a `ThreadedConnectionPool` per call via `get_connection()` (commit-on-success, rollback+return-to-pool on exception — see "Performance" below for why this is a pool and not a bare `psycopg2.connect()` per call). Rows are `RealDictRow`s (dict-like, `row["column"]`). `init_db()` creates the schema (`families`, `family_members`, `reminder_times`, `walks`, `treatments`) and is called by both processes at startup — it's safe to call repeatedly (see the `family_id` column check before dropping the old chat_id-schema `walks` table; **never** make that drop unconditional, it would wipe live walk history on every restart).
- `api/auth.py` — validates Telegram WebApp `initData` (HMAC-SHA256 per Telegram's documented algorithm) from an `Authorization: tma <initData>` header. `get_telegram_user` validates only; `get_current_member` additionally requires existing family membership (`db.get_member_by_tg_user_id`). A Mini App user's `tg_chat_id` is always set equal to their `tg_user_id` at family-creation/join time — Telegram private chat_id == user_id, and initData never exposes a separate chat_id, so there's no other source for it.
- `api/routers/*.py` — one router per resource (`family`, `walks`, `treatments`, `stats`, `export`), thin: validate via `Depends(get_current_member)`, call `db.*`, return pydantic models from `api/schemas.py`.
- `api/constants.py` — urgency threshold (`URGENCY_SOON_DAYS`) and category labels; `compute_status(interval_days, treated_on)` is the single source of truth for status color/days-remaining/progress-bar-percent, computed server-side and sent to the Mini App as data, not recomputed in JS. There's no per-category hardcoded interval anymore (see "Treatments" below) — `compute_status` takes `interval_days` as an argument, read off the specific treatment record.
- `miniapp/` — vanilla HTML/CSS/JS, **no build step**, loaded as native ES modules (`<script type="module">`). `js/api.js` is the only place that calls `fetch()`; every screen module (`today.js`, `medicine.js`, `stats.js`, `onboarding.js`, `settings.js`) imports it rather than calling `fetch` directly. `js/state.js` holds the tiny in-memory session state (`family_id`, member roster for avatar colors/name lookups) populated once from `/api/auth` after login, and re-populated by `settings.js` whenever the Settings tab is opened (it's the only screen that mutates family-level state, so it always fetches fresh rather than trusting the cached copy). `js/time-list.js` is a small reusable "list of HH:MM rows with add/remove" component shared by onboarding's fixed-mode step and Settings' reminders block — don't duplicate that logic if you touch either.

## Reminder scheduling model

This is the part that's easy to get wrong, because it spans two processes that don't talk to each other directly:

- The old (pre-Mini-App) bot rescheduled a reminder **synchronously**, in-process, the instant a walk button was pressed. That doesn't work anymore: walks are now written by the **api** process, but `job_queue` jobs live in the **bot** process's memory. There is no IPC between them.
- Instead, `bot.py` runs `reconcile_reminders()` on a `run_repeating` job (every 5 minutes) **and** once at startup via `post_init()`. Each tick fully rebuilds the managed jobs (`reminder_interval_*`, `reminder_fixed_before_*`, `reminder_fixed_at_*`) from the current DB state (`families`, `reminder_times`, last walk) — Postgres is the single source of truth, not the process's memory. This replaces both the old `post_init`-only restart recovery *and* the old instant-reschedule-on-walk.
- `interval` mode: one `run_once` job per family, timed at `last_walk.walked_at + interval_hours` (or `family.created_at` if no walk yet). `send_interval_reminder` re-checks `get_last_walk` before actually sending — if a walk landed after the job was scheduled, it silently skips (the next reconciliation tick will have already computed the correct next time).
- `fixed` mode: `run_daily` jobs per `reminder_times` row, for "1h before" and "at time" (both fire unconditionally — only the "+1h after" follow-up is conditional). The "+1h after" nudge (`send_nudge`, shared with interval mode) is scheduled dynamically via `schedule_once()` (cancel-by-name then `run_once` — the same pattern the old `reschedule_reminder` used) and checks `get_last_walk` before sending, so it silently no-ops if the walk was already logged. This is how "cancel the remaining reminder after a walk is logged" (per the spec) is achieved *without* cross-process job cancellation.
- All reminders go to **every** `family_members.tg_chat_id`, not a single `chat_id` — see `send_to_family()`, which catches `TelegramError` per-recipient so one blocked/broken chat doesn't stop the rest of the family from being notified.
- `fixed`-mode times are timezone-aware: `families.timezone` (IANA name, e.g. `Europe/Moscow`) is auto-detected client-side via `Intl.DateTimeFormat().resolvedOptions().timeZone` at family creation (no onboarding step needed) and validated server-side in `CreateFamilyRequest` against `zoneinfo.available_timezones()`. `schedule_fixed_reminders()` attaches it via `time_of_day.replace(tzinfo=resolve_timezone(...))` before calling `run_daily` — PTB uses the tzinfo on the `time` object directly if present, no JobQueue-level default to configure. `resolve_timezone()` falls back to UTC (logging a warning) rather than raising, so one family's bad/legacy tz value can't take down reconciliation for everyone. Gotcha if touching this: use `.timetz()`, not `.time()`, when re-deriving a time-of-day from datetime arithmetic (e.g. the "1h before" offset) — `.time()` silently drops the tzinfo.

## Onboarding / auth flow

No `ConversationHandler` in the bot anymore — onboarding is entirely in the Mini App (`miniapp/js/onboarding.js`) calling `POST /api/family` (create) or `POST /api/family/join` (second member, via `/start invite_<code>` deep link → bot passes the code through in the WebApp button URL → Mini App auto-joins on load, skipping the onboarding steps). `compute_interval()`/breed/age heuristics from the old bot are gone entirely — `interval_hours` is now a direct user input.

`families.pet_sex` (`'male' | 'female'`, defaults to `'female'`) is collected as a segmented toggle on onboarding step 1, next to the name field — it exists purely for Russian grammatical agreement (e.g. the Today mood card picks "бодр"/"заждался" vs "бодра"/"заждалась" off `state.petSex` in `today.js`), not a product feature in its own right. Any new user-facing text that needs to agree in gender with the pet should read `state.petSex` client-side rather than hardcoding one form.

## Settings tab

`miniapp/js/settings.js` is the 4th nav tab and the only place (besides onboarding) that can mutate `families` after creation. Four blocks, each independently saved:

- **Профиль** → `PATCH /api/family` (`UpdateProfileRequest`, partial via `exclude_unset`) → `db.update_family_profile`.
- **Напоминания** → `PATCH /api/family/reminders` (`UpdateRemindersRequest`, shares its mode/times/interval_hours validation with `CreateFamilyRequest` via the `ReminderConfigBase` mixin in `api/schemas.py` — extend that base if the shared rule needs to change, not both subclasses separately) → `db.set_reminder_config`. No timezone field here; that's set once at family creation and isn't editable. Saving doesn't push anything to `bot.py` — the next `reconcile_reminders()` tick (≤5 min) picks up the change, same as any other DB-side reminder edit.
- **Семья** → re-displays `invite_url` (now also returned by `/api/auth`, not just at creation time — it used to be shown once and lost if not copied) and the member roster from `AuthResponse.members`.
- **Экспорт истории** → `GET /api/export/walks` / `GET /api/export/treatments`, both `text/csv` with `Content-Disposition: attachment`. Since Mini App auth is a custom header (not a cookie), a plain `<a href>` download won't carry it — `api.js`'s `requestBlob()` fetches with the header manually and `settings.js`'s `downloadCsv()` turns the blob into an object URL + synthetic `<a download>` click. Two separate files, not one with multiple sheets (plain CSV has no sheet concept).

Both PATCH endpoints return a full `AuthResponse` (via the shared `_build_auth_response()` helper in `api/routers/family.py`) so the frontend never needs a follow-up `/api/auth` call after saving.

## Treatments — interval_days is per-record, not per-category

`treatments.interval_days` (user-entered, default 30) replaced what used to be a hardcoded per-category interval (ticks≈30d/deworming≈90d/vaccine≈365d) — different drugs in the same category legitimately have different durations (e.g. two different tick treatments at 28 vs 35 days), so the interval can't be a category constant. `compute_status()` in `api/constants.py` now takes `interval_days` directly rather than looking it up by category. The old per-category numbers still exist, but only as **client-side UI defaults** (`DEFAULT_INTERVAL_DAYS` in `miniapp/js/medicine.js`) prefilled into the add-treatment form's number input and refreshed when the category dropdown changes — they're a suggestion, not enforced anywhere server-side.

## Performance — Mini App slow to open

Investigated once (loading felt slow on open in Telegram); fixes and diagnostic tooling from that pass:

- **Fixed:** `main.js` was calling `/api/auth` twice on every load — once in `boot()` to decide onboarding-vs-main-screen, then again unconditionally inside `enterMainApp()`. `enterMainApp(auth, prefetchedWalks)` now takes the already-fetched auth (and, where available, an already-started `getWalks` request) instead of re-fetching. Only the `onboarding-complete` handler still calls `enterMainApp()` with no args (needs a *fresh* auth after just creating/joining a family).
- **Fixed:** `boot()` now fires `/api/auth` and `/api/walks` **in parallel** via `Promise.all` instead of sequentially — `getWalks` doesn't depend on any data from the auth response (the server independently resolves the caller's family via `get_current_member` on each request), so waiting for auth to finish before even starting the walks request was pure lost time. The walks call is `.catch(() => null)`-guarded since it 404s harmlessly for a not-yet-onboarded user (no `family_id` yet).
- **Fixed:** `database.py`'s `get_connection()` used to open a brand-new `psycopg2.connect()` (fresh TCP+TLS+Postgres-auth handshake) on *every single call*, no reuse. Since most handlers make several `db.*` calls per request (`/api/auth`'s `_build_auth_response()` alone calls `get_member_by_tg_user_id` + `get_family` + `get_family_members` + conditionally `get_reminder_times` — up to 4), this meant up to 4 full connection handshakes serialized inside one HTTP response. Replaced with a lazily-initialized `psycopg2.pool.ThreadedConnectionPool(1, 10, ...)` — `get_connection()`'s public interface (context manager, same call sites) is unchanged, only the internals borrow-and-return instead of connect-and-close. This was the single highest-confidence fix in the pass; everything else here is smaller in comparison.
- **Fixed:** missing indexes — `family_members(tg_user_id)` (hit on *every* authenticated request via `get_current_member`), `family_members(family_id)`, `walks(family_id, walked_at DESC)` (matches the actual `get_walks` query shape), `treatments(family_id)`, `reminder_times(family_id)`. Added as `CREATE INDEX IF NOT EXISTS` in `init_db()`, same idempotent-migration pattern as the rest of the schema.
- **Fixed:** the Telegram WebApp SDK `<script src="https://telegram.org/js/telegram-web-app.js">` in `index.html`'s `<head>` had no `defer` — a classic blocking script, so the browser couldn't even start discovering/fetching `js/main.js` (an ES module, deferred by default) until that external-CDN script finished downloading and executing. Added `defer`; execution order is preserved (deferred scripts, including modules, run in relative document order) so `main.js` still only runs after `Telegram.WebApp` is available.
- **Diagnostic tooling left in place** (not a one-off, safe to keep): `api.js`'s `request()`/`requestBlob()` log every call to the browser console — sequence number, method, path, start offset (`performance.now()`, so overlapping timestamps = parallel, non-overlapping = sequential), total client-observed round-trip, and the server-reported time (see next point). `api/main.py` has an HTTP middleware (`log_request_timing`) that logs and returns an `X-Response-Time-Ms` response header per request — the gap between the client's `total` and this `server` value is network/cold-start time, not FastAPI/Postgres time. `database.py` has a `DB_TIMING_LOG=1` env-gated per-call timing log (off by default — noisy, since a single request can make several `db.*` calls) for isolating Postgres-side latency specifically.
- **Not fixed, not verifiable from here:** Railway cold starts. Whether the `api` service is sleeping-on-idle and taking multiple seconds to spin back up on the first request after inactivity can only be confirmed in Railway's own service logs/dashboard (look for a gap between "container starting" and the first request timestamp lining up with slow loads) — there's no way to check this from the codebase or this sandbox. If it *is* the dominant cause: a low/free Railway plan will sleep regardless of app-level optimization, and the only real fixes are a paid always-on plan, or an external cron/uptime-ping hitting the api service every few minutes to keep it warm (a real workaround, but paying for uptime is the more honest fix if this app needs to feel instant). `GET /health` exists specifically to be a cheap ping target for this — it does not touch Postgres, only confirms the process itself is up.

### Real production bug found in the same pass: cold start was showing the wrong error screen entirely

Two users reported the Mini App showing `screen-outside-telegram` ("Open Barbos in Telegram") **while opening it correctly via the bot's WebApp button** — misleading, since that screen is meant for "you didn't open this via Telegram at all." The actual cause: `boot()`'s `try/catch` around the initial `/api/auth` call caught *any* failure (network error, 5xx, cold-start delay) and funneled it into the exact same `showScreen("outside-telegram")` call used for missing `initData` — conflating "definitely not in Telegram" with "in Telegram, but the first request failed." One user's "it loaded when I tried again a bit later" is exactly what you'd expect if the real cause was a cold `api` container.

Fixed by splitting these into genuinely different states: `loadMainScreen()` (factored out of `boot()` so a retry doesn't re-run the one-time event-wiring calls and double-attach every click handler) now retries the auth+walks fetch once automatically after `AUTH_RETRY_DELAY_MS` (2.5s) before giving up, and only *then* shows a new, distinct `screen-load-error` ("сервер не отвечает, попробуйте снова" + a `btn-retry-load` button that re-calls `loadMainScreen()`) — never the "open in Telegram" copy, since by construction we only reach this code path with valid `initData` already confirmed present. If this fires often in practice, the retry delay/count here should be the first place to look before treating it as purely a Railway-tier problem.

## Language

All user-facing strings, comments, and docstrings in this codebase are in Russian. Match that when adding to `bot.py`/`database.py`/`api/*`/`miniapp/*`/`README.md` unless told otherwise.
